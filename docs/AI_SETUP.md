2026-10-07追記：この環境はキー設定・実API試験を実施済み。Vercel発行のキーはVercel互換経路へ送るよう修正し、Jev・OpenAI双方の接続と同じ48問での実通信を確認した。[現在の実測と修正内容](VERCEL_JEV_FIX_2026-10-07.md)。以下の「現在の状態」は2026-10-06時点の記録。

## 現在の状態

Jevによる質問・資料・取扱分野の判断と、OpenAI / Geminiによる会話文の生成を実装した。OpenAIの回答は、検証を通った段落から順次表示する。

この環境のAPIキーは未設定。実APIとの疎通・日本語での回答品質・実際の応答時間は未確認である。現在の管理設定はローカル応答。接続コードの実装完了と、外部サービスの接続完了を混同しない。

仕入先Excelは既に登録済み。再アップロードは不要。登録状況は [仕入先情報の記録](SUPPLIER_KNOWLEDGE_REPORT.md) を参照する。

## 利用者に必要な操作

1. [TypeSafeのコンソール](https://console.typesafe.ai/) と [OpenAIのAPIキー画面](https://platform.openai.com/api-keys) でキーを用意する。値をチャット・メール・Gitに貼らない。
2. プロジェクト直下の既存 `.env.local` に次の値を設定する。管理者パスワード・セッション設定等は保持する。

   ```dotenv
   TYPESAFE_API_KEY=発行したJevのキー
   # Vercel AI Gateway発行のキーなら次の接続先を指定
   TYPESAFE_API_BASE_URL=https://ai-gateway.vercel.sh/typesafe
   OPENAI_API_KEY=発行したOpenAIのキー
   OPENAI_MODEL=gpt-4.1-mini
   ```

   TypeSafeのコンソールから直接発行したキーの場合は `TYPESAFE_API_BASE_URL=https://api.typesafe.ai` を使う。VercelのキーをTypeSafe直接APIへ送ると認証に失敗する。この環境では既存のキー名 `TYPESAFE_API_KEY` を維持し、接続先を切り替える。

3. 開発サーバーを再起動する。キー保存後に担当エージェントへ「保存した」と伝えれば、再起動・設定・接続確認を依頼できる。値そのものは共有しない。
4. `/admin?tab=settings` で「Jev＋OpenAIの構成を選ぶ」→「設定を保存する」。JevとOpenAIの「接続を確認」を実行する。少量のAPI利用が発生する。
5. 「実際のAPIへの接続と応答形式を確認しました」と確認日時・所要時間が出ることを確認する。キーの存在だけでは接続成功と表示しない。モデル名やキーが変わった場合、以前の接続結果は表示しない。
6. 「液体の流れを止める部品を探したい」→「水に使います」など、用途を言い換えた相談で実回答を確認する。商品台帳の納期確認は「DEMO-GLASS-01」→「いつぐらいに届く？」で検証できるが、デモ値を実販売条件として扱わない。

外部Webから未知の商品を探す場合、`EXA_API_KEY` または `TAVILY_API_KEY` も設定し、管理画面のWeb検索と検索サービスを有効にする。登録済みURLの同期と、外部検索サービスは別の設定である。Jevのキーだけでインターネット検索が有効になるわけではない。

OpenAIの代わりにGeminiで回答を生成できる。`GEMINI_API_KEY` を設定し、回答生成の方式をGeminiにする。既定モデルは `gemini-2.5-flash`。質問の判断もGeminiを選べるが、今回のJevによる分野・資料の選択と同じ機能ではなく、質問意図の抽出が中心である。

## 処理の役割

質問ごとの詳しい振り分けと変更時のテスト条件は [ローカル処理とAIの役割](CHAT_ROUTING.md) を参照。登録情報の回答、用途相談、両方を含む質問をコードで分けている。

| 段階       | 実装                                                                                                 |
| ---------- | ---------------------------------------------------------------------------------------------------- |
| 質問の整理 | 明確な型番・追加の価格/在庫/納期質問はローカルで処理。曖昧な相談はJev等で分類                        |
| 資料検索   | 取込済み文書の候補をローカルで選び、必要に応じてExa/Tavilyで公開Webを検索                            |
| Jevの判断  | `state`に直近6メッセージと資料候補、`questions`に意図・分野・関連資料の選択肢。選択肢と信頼度を検証  |
| 回答生成   | OpenAI Responses API、またはGemini。公開可能な根拠・回答制約・会話履歴から短い日本語文を生成         |
| 回答の検査 | 出力形式、根拠ID、未提供数値、非公開の取引先名、取扱未承認時の販売断定、非表示項目、注文完了等を検査 |
| 表示と保存 | OpenAIは完全なJSON段落を検査してからSSEで表示。完了した会話はSQLiteに保存                            |

販売承認、公開可否、金額計算、見積・注文操作は従来の業務処理が担当する。Jev・回答生成モデルに注文ツールは渡していない。資料で見つかったことと、この会社から販売できることを区別する。

非公開の仕入先一覧は、承認済みの公開用分野名だけをAIに渡す。社名、HP、原文、内部メモ、取引条件は渡さない。非公開文書は本文・ファイル名の代わりに一般的な「関連資料あり」の情報を使う。公開文書の抜粋は外部モデルに送信される。履歴は現在の公開設定で再確認し、根拠が変わった生成文はそのまま再利用しない。

## 応答速度

- 型番が確定した照会と、商品が確定した価格・在庫・納期の追加質問では、外部AI/Web通信を省略する。
- 登録商品名の照会、数量計算、見積・注文案内、あいさつもローカルで処理する。型番が確定していても用途・仕様の相談は生成AIの対象。
- 分野が明確な用途相談は分類APIを省略して回答生成へ進む。あいさつは生成APIも省略する。
- 必要なWeb検索と質問分類は並行実行する。
- AIへ渡す会話は直近6メッセージ、資料は最大8候補・短い抜粋に制限する。
- OpenAIは最後まで待たず、検査を通った段落から表示する。文字を一字ずつ遅らせる演出は入れない。Geminiの代替接続は一括生成後の表示。
- 分類4秒、Web検索5秒、回答生成8秒の通信期限。チャット全体は13秒、ブラウザーは18秒で打ち切る。通常の目標応答時間を示す値ではない。
- 失敗したモデルへの自動再試行は行わず、登録情報からの回答へ切り替える。通信切断は外部生成にも伝える。
- 会話取得は会話IDの索引を使用し、他の利用者の全メッセージを読み込まない。

実APIの所要時間は、キー設定後に最初の回答表示までと回答完了までを測定する。接続確認の所要時間はその時の小さな試験1件の値であり、本番の平均値や最大値ではない。

## 実装ファイル

- `lib/server/providers.ts`: Jev/Geminiの質問分類、Exa/Tavily検索。
- `lib/server/retrieval.ts`: 文書候補の抽出。
- `lib/server/ai-responses.ts`: 生成API、段落の構造化出力・検査・途中表示。
- `lib/server/chat.ts`: 検索・業務ルール・生成を統合。生成文の根拠ハッシュと履歴の再確認。
- `lib/server/ai-setup.ts`: 実APIの接続試験。状態と所要時間を保存。
- `app/api/[...path]/route.ts`: `POST /api/chat` のSSE、`POST /api/admin/providers/:id/test`。
- `components/AdminSettings.tsx`: 必要なキー・未接続状態・接続確認を表示。
- `components/ChatWidget.tsx`, `components/api.ts`: 段落の途中表示と最終会話への置き換え。

`POST /api/chat` は `Accept: text/event-stream` のとき `data: {"type":"status|text|result|error","data":...}` を返す。`text` は累積本文、`result` は従来のChatResponse。通常のJSONクライアントも維持する。管理設定に `responseProvider`, `responseModel` を追加し、既存DBには既定値を補完する。

## 検証と限界

モックでは、Jevの分野選択→生成、段落完了前の非表示・完了後の表示、分割UTF-8、未提供数値・非公開名・不正根拠IDの拒否、API失敗、履歴の再検査、即答時の外部通信なしを確認する。ブラウザーでは本物のローカルSSE通信と、最終結果を保留する模擬通信で途中表示を確認する。

構造化出力・文字列検査だけで意味の正しさを保証することはできない。実際の匿名化した問い合わせで、根拠との整合、具体的な次の質問、誤った販売断定、費用、応答時間を接続後に評価する。APIキーがない状態で実モデルの品質・速度を確認済みと報告しない。
