## どのAPIを何に使うか

| API            | 用途                                                               | HTTPリクエスト                                                       | 送信する内容                                                                           | 返答の利用                                                                           |
| -------------- | ------------------------------------------------------------------ | -------------------------------------------------------------------- | -------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| Jev / TypeSafe | 質問の意図、前の商品の続きか、公開取扱分野、資料候補の関連性の判定 | `POST https://api.typesafe.ai/v1/systemone` / JSON / Bearer認証      | `model`、JSON文字列の`state`（質問・直近履歴・資料候補）、`questions`（Choice / Noul） | 既知の分類・信頼度を検証し、照合や回答経路に使う。失敗時はローカル分類               |
| OpenAI         | 用途・仕様・選び方について、根拠と会話に沿った日本語の相談文を生成 | `POST https://api.openai.com/v1/responses` / JSON / Bearer認証 / SSE | `model`、指示、JSON文字列の`input`（質問・直近履歴・公開事実・制約）、出力JSONスキーマ | 段落ごとに根拠・数値・非公開情報等を検証。通過した本文を表示し、拒否時は定型文へ戻る |

現在のモデルはJev `jev-latest`、OpenAI `gpt-4.1-mini`。OpenAIは `store:false`、`stream:true`、`max_output_tokens:900`、`strict`なJSONスキーマを指定している。登録価格・在庫・納期・金額計算はローカル処理で扱うため、すべての質問に両APIを呼ぶ構成ではない。

リクエスト形式と使用量の取得項目は公式資料でも確認した。Jevはレスポンスの`usage.input_tokens`と`usage.output_tokens`、OpenAIはストリーム完了イベントの`response.usage`を読み取る。[TypeSafe公式API仕様](https://docs.typesafe.ai/api)、[OpenAI公式ストリームイベント仕様](https://developers.openai.com/api/reference/resources/responses/streaming-events)。

管理画面の詳細には実際に送ったパラメーター、入力項目名、履歴件数、公開事実件数、送信JSONのUTF-8バイト数を記録する。APIキー、Authorizationヘッダーの値、質問本文、資料本文、生成本文、提供元エラー本文をAPI利用ログへ保存することはない。質問との対応は、既存の管理者専用会話記録を質問IDで参照する。

## 今回、原因を確定できたこと

- 数値チェック拒否が8件。顧客の寸法・荷重等を受けた会話が定型文へ戻る際の、実際の拒否理由を確認できた。コードの許可数値は登録事実等から作られ、質問・履歴の数値は許可集合に入っていない。顧客提示の条件の復唱と、会社が保証する数値を区別する必要がある。
- 送料などの業務事実チェック拒否が1件。原因コードを記録することで、接続障害と区別できた。
- 要約・質問付きのお礼・一部の選定相談をローカル処理へ振り分け、APIを呼ぶ前に意図を取り落とすケースがある。キー修正に加え、回答経路の修正が必要。
- 型番・用途・数量の引き継ぎと、担当者へ渡す文章の作成は引き続き弱い。
- 採用された技術相談にも、材料全般の性質を一律に言う、条件確認前に「保護カバーなどで覆うと安全です」と言い切る例が残る。技術的な正確性の確認と担当者確認へつなぐ表現の改善が必要。今回、各材料の技術的正誤を外部資料で全件検証したわけではない。

今回は利用記録と追加検証を実装した。上記の会話不具合を修正済みとは報告しない。

## 記録機能の実装と検証

呼び出し開始時にSQLiteの`ai_calls`へ保存し、完了時にHTTP状態・処理時間・採否・許可したエラーコード・取得済み使用量を更新する。切断等で完了記録がないものは「完了記録なし」として残る。質問IDは保存される顧客メッセージIDと一致する。

数値等の検証で本文が拒否された場合も、その本文を表示せず、ストリームを完了まで受け取って使用量を取得する。既存の時間・サイズ・出力トークン上限は維持する。タイムアウトや中断で取得できない使用量をゼロとして扱わない。

管理者専用APIは `GET /api/admin/ai-usage`。`provider`、`scope`、`since`、`until`、`conversationId`、`turnId`で絞り込み可能。`limit`は明細の上限、集計全体の上限ではない。

PC・スマートフォン相当の実ブラウザ操作で、画面表示、API絞り込み、質問/回答モーダル、JSON保存を確認。未認証取得は401、不正な絞り込みは400。ページ横はみ出し・JavaScript例外・ダウンロード内のAPIキー露出は検出なし。

型チェック、関連テストと全体92テスト、本番ビルドで確認した。キー、元DBのプロバイダー設定、実注文・メール送信の設定は変更していない。
