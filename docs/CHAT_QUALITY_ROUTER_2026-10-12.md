# 会話品質の改善と振り分けの見直し（2026-10-12）

## 依頼

- 条件を伝えたお客様に「もう少し詳しく教えていただけますか？商品名・型番、または『高温の炉で使うガラス』のような用途からお探しします。」が返り、会話の流れが止まる。この状況でこの定型文を返さないこと。
- 質問・要望に情報で応え、担当者への相談（アポイント）につながる会話にすること。
- 定型文か生成AIかを決める仕組みを置くか、置くならOpenAIとJevのどちらが適しているかを判断すること。
- より多様な会話・質問で試験すること。

## 原因

2026-10-07の試験記録（`.data/verification/live-ai-2026-10-07/`）から特定した。

1. お客様自身が書いた数値（25A、40度、100ミリ、20個など）を回答に含めると、生成AIの回答が「根拠のない数値」として不採用になっていた。Jev接続修正後の48問では、OpenAIの不採用10件のうち9件がこの理由だった。
2. 不採用時の代わりに、会話と関係のない定型文（上記）や、分野・商品の決まり文句を表示していた。
3. 振り分けに次の誤りがあった。
   - 「ありがとう。さっきの台車の件ですが…」をあいさつだけと判定し、「どういたしまして」で終えていた。
   - 「まとめて」「担当者に渡したい」「問い合わせに使う文章を作って」を判定できず、分野の決まり文句を返していた。
   - 条件付きの質問（「150キロ、通路900ミリ。この条件で決められますか？」）を、登録商品の照会として扱っていた。
   - Jevが推定した分野が直前の商品を上書きし、数量を変えた質問で型番を聞き直していた。
   - 「10個は確保できる？」に「はい、取り扱っています」と答えていた。
4. 通常サイトのDB（`.data/aokienji.sqlite`）は、回答生成AIが未設定（ローカル応答）のままだった。この設定では、相談はすべて定型文になる。

## 判断：振り分けの仕組みと、OpenAIとJevのどちらを使うか

振り分けの仕組みは置いた。ただし、外部AIではなくコード（`lib/chat-policy.ts`）で判断する。

- 定型文かAIかは「登録データで正確に答えられる質問か」で決まる。価格・在庫・納期の計算、非公開情報、手続き、送料・値引き・支払などの方針は、アプリが正確に答える。それ以外の会話は生成AIが答える。この判断は数ミリ秒で終わり、外部の通信や失敗が入らない。
- 「どの分野の話か」の理解は、OpenAIが回答を書く中で行う。会話全体と、分野ごとの確認項目を渡している。

OpenAIとJevの比較は、同じ61問で行った（下表の「推奨構成」と「Jev＋OpenAI」）。

| 指標                             | 推奨構成（OpenAIのみ） | Jev＋OpenAI                         |
| -------------------------------- | ---------------------- | ----------------------------------- |
| 評価：良好 / 一部不足 / 改善必要 | 40 / 21 / 0            | 41 / 17 / 3                         |
| どちらが良いか（伏せて比較）     | 16問で優位             | 11問で優位（同等34問）              |
| Jevの分類                        | 呼ばない               | 27回中13回が信頼度不足で不採用      |
| 追加の利用量                     | なし                   | Jev 1回あたり入力約1,700・出力約560 |
| 追加の待ち時間                   | なし                   | Jev 1回あたり中央値約0.5秒          |

Jevは回答の質を上げず、待ち時間と利用量だけが増えた。そのため推奨構成はOpenAIのみとした。Jevは管理画面の選択肢として残す。Jev＋OpenAIの「改善必要」3件は、AIの技術説明の誤り（600度の窓にホウケイ酸ガラスを候補に挙げた）、伝えた個数の聞き直し、おすすめの種類への無回答。

## 変更内容

### 振り分け（`lib/chat-policy.ts`）

- あいさつ・お礼で始まる本題を、本題として扱う。
- 次を判定する理由コードを追加した。
  - `summary`：要約の依頼。「まとめて見積」は要約と区別する。
  - `handoff`：担当者への相談・電話・入力場所の質問。
  - `transaction`：注文・見積・取り置き・「もう送信された？」。
  - `policy`：送料・値引き・支払・急ぎ・所在地・営業時間・現地調査・据付・サンプル・カタログ・約束・取り寄せ。
- 手続き・方針の回答はアプリが行う。条件や選定の質問を含む場合だけ、生成AIが補足する。
- 「はい」「お願いします」「わかりません」は、直前の会話への返事として生成AIに回す。
- 材料記号（SUS304、SS400等）を型番として扱わない。英語の価格・納期・数量（5 pcs）も扱う。

### 生成AI（`lib/server/ai-responses.ts`）

- 指示を「質問に直接答える、伝えられた条件を聞き直さない、確認は最大1つ、条件がそろったら担当者へ」に変えた。
- お客様のこれまでの発言、分野ごとの確認項目、会社の公開情報、相談方法を根拠として渡す。
- お客様の数値は回答で繰り返してよい。ただし、価格・割引の言い切り（「価格は1万円です」「2割引になります」）は、お客様が書いた金額でも拒否する。
- 「お約束できません」のような否定文は拒否しない。約束・販売の断定・根拠のない対応範囲（英語対応等）は拒否する。
- 拒否したときは、理由を添えて1回だけ書き直させる。存在しない根拠IDは、文章を拒否せず根拠IDだけを取り除く。
- 確定回答の後に続ける補足では、確定回答と同じ内容の段落を表示しない。

### AIを使わないとき（`lib/server/consultation.ts`）

- 話題（バルブ、パッキン、ガラス、断熱材、金網、ホース、ポンプ、スタッド、台車、炉内の部品、工具、継手、鋼材、製作品）ごとに確認項目を持つ。
- お客様の条件（数値・材質・流体など）を復唱し、まだ伺っていない項目を1つだけ聞く。「分からない」と言われた項目と、一度聞いた項目は聞き直さない。
- 要約はお客様の発言を箇条書きにし、未確認の項目を添える。
- 支払・送料・値引き等の方針には、決まった文で答える。

### 文脈と計算（`lib/server/chat.ts`, `lib/server/chat-replies.ts`）

- 「税込み・送料込みだと合計いくら？」「来週月曜までに大阪に届く？」は、直前の商品について答える。
- 支払や送料の質問をはさんでも、話していた商品を引き継ぐ。
- 数量の単位（本・枚）を保持する。税込金額を計算し、送料が未確定であることを伝える。
- 希望日が伝えられていれば、同じ質問をしない。
- 確認用（デモ）商品かどうかを聞かれたら、そのことを伝える。
- 一度担当者へ送った会話には「受け付け済み」と答える。

### 担当者への引継ぎ（`components/ChatWidget.tsx`, `app/contact/page.tsx`）

- 次のとき、最新の回答の下に「この内容で担当者に相談する」ボタンを表示する。登録商品の価格を確認した場合は「この内容で見積を依頼する」。
  - 相談が2往復以上続いたとき
  - 要約・手続き・相談方法の質問のとき
- ボタンを押すと、会話IDを付けて問い合わせフォームを開き、「ご相談内容」にお客様の発言（またはAIの要約）を入れておく。

### 管理画面（`components/AdminSettings.tsx`）

「OpenAIの構成を選ぶ（推奨）」ボタンを追加し、役割の説明を更新した。

## 運用上の注意と残る課題

- 通常サイトで生成AIを使うには、管理画面の「設定」で「OpenAIの構成を選ぶ（推奨）」→「設定を保存する」→「接続を確認」を実行する。この作業では通常サイトのDBの設定は変更していない。AIなしでも例の定型文は返らないが、説明を求める質問には答えられない。
- AIの一般的な技術説明には誤りが残りうる。評価では、Jev＋OpenAI構成の回答で「600度の窓にホウケイ酸ガラス」「蒸気用パッキンにシリコン系」という疑問のある例が指摘された。回答を書くモデルは推奨構成と同じため、推奨構成でも起こりうる。数値の捏造は検査で防いでいるが、材質の向き不向きの判断は担当者の確認が前提である。より上位のモデルに変えると改善が見込めるが、費用は増える（未検証）。
- 「はい」「それで」のような短い返事に、同じ確認項目を繰り返し並べる傾向が残る。
- 引継ぎボタンの表示による問い合わせ件数（アポイント率）の変化は、本番の問い合わせで測る必要があり、まだ測定していない。
- 試験は確認用（デモ）の商品データで行った。実際の商品台帳では、商品名の一致の仕方が変わる場合がある。
