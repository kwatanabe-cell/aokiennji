# ローカル処理・Jev・回答生成AIの役割

2026-10-06作成、2026-10-13更新。「登録情報で確定できることはローカルで正確に答え、それ以外の会話は生成AIが会話の流れを踏まえて答える」という基準。2026-10-12に、条件を伝えたお客様へ「もう少し詳しく教えていただけますか？商品名・型番…」という定型文が返る問題を解消した。経緯と試験結果は [会話品質の改善と振り分けの見直し](CHAT_QUALITY_ROUTER_2026-10-12.md) を参照。

## 振り分け表

振り分けは `lib/chat-policy.ts` の `planChatRoute` がコードで決める（外部APIを使わず数ミリ秒）。生成AIを使うかどうかの判断に、Jev等の分類APIは必要としない。

| 質問・処理                                                                         | 理由コード      | 回答                                                        | 生成AI（OpenAI等）                   |
| ---------------------------------------------------------------------------------- | --------------- | ----------------------------------------------------------- | ------------------------------------ |
| 仕入先名・取引条件・公開範囲                                                       | `privacy`       | 非公開方針（ローカル）                                      | 使用しない                           |
| あいさつ・お礼だけ                                                                 | `social`        | ローカル。「ありがとう。さっきの件ですが…」は本題として扱う | 使用しない                           |
| 「まとめて」「担当者に送る文章を作って」                                           | `summary`       | 生成AIが要約。失敗時はお客様の発言を箇条書き                | 使用                                 |
| 見積・注文の依頼・取り置き・「もう送信された？」                                   | `transaction`   | 手続きをローカルで回答                                      | 条件・選定の質問を含むときだけ補足   |
| 担当者・電話・入力場所                                                             | `handoff`       | 相談方法をローカルで回答                                    | 条件・判断の質問を含むときだけ補足   |
| 送料・値引き・支払・急ぎ・所在地・営業時間・見積の回答時期・引き取り・社内加工か等 | `policy`        | 決まった方針をローカルで回答                                | 条件・相談・他の質問を含むときは補足 |
| 登録商品の価格・在庫・納期・数量・税込計算                                         | `facts`         | 登録値から計算（ローカル）                                  | 用途相談を含むときだけ補足           |
| 分野しか分からない価格・納期（相談の途中）                                         | `facts`         | 担当者が見積もる旨をローカルで回答                          | 補足（何が分かれば見積れるか等）     |
| 商品が未特定の価格・納期（会話の最初）                                             | `clarification` | どの商品か確認（ローカル）                                  | 使用しない                           |
| 用途・仕様・比較・条件の説明・不具合の相談                                         | `consultation`  | 生成AI                                                      | 使用                                 |
| 曖昧な説明・「はい」「わかりません」等の返事                                       | `discovery`     | 生成AI                                                      | 使用                                 |
| 型番・商品名・分野だけの照会                                                       | `lookup`        | 登録情報（ローカル）                                        | 使用しない                           |

「ローカル」は、このアプリのサーバーと登録DBによる処理を指す。

「注文」「見積」という語があるだけでは手続きとして扱わない（2026-10-13）。「注文したい」「見積をお願いします」のような依頼だけを `transaction` にし、「今日注文したら最短いつ出荷？」は納期の質問、「見積を依頼した場合、回答はいつ？」は見積の回答時期の質問として答える。「在庫の話ではなく」「注文じゃなくて」のように否定された語も質問として扱わない。

### 決まった文は会話中1回

方針・手続き・「担当者が確認してご案内します」などの決まった文は、1つの会話で1回だけ表示する（電話番号の有無だけが違う文も同じ文とみなす）。同じ質問が続いたときは、生成AIが会話の流れに沿って答え、決まった方針は `policies` として生成AIに渡す。生成AIが使えないときだけ、決まった文をもう一度表示する。登録商品の価格・在庫・納期は聞かれるたびに答える。

### AIが使えないとき・繰り返しを省いたとき

- 決まった文を省いた結果、生成AIも使えない場合は、省いた文をもう一度表示する。返答の本文が空になることはない（最後に必ず文を入れる）。
- OpenAIが残高不足（`insufficient_quota`）を返したら、10分間はOpenAIを呼ばずにすぐ組み立て文で答え、担当者向けのAI調査も止める。管理画面の概要に残高不足を表示する。
- 組み立て文でも、条件の復唱（「伺った条件（…）」）、確認の聞き方、ボタンの案内は会話中1回にする。2回目以降は新しく伺った条件と、次に知りたい点だけを短く書く。

### 数量・品目の読み取り（2026-10-13追加）

- 1つの文に数量が複数あるときは最新の値（「40個から60個に」は60個）を使う。「1個あたり」「1本いくら」は数量にしない。
- 「1個あたり8,400円で合っていますか？」のように金額を挙げた確認は、その単価の登録商品に戻って単価で答える（間に別の品目の話があっても）。
- 「℃」は正規化で「°C」になるため、どちらも温度として扱う（表示は「℃」）。
- 「ポンプ側の振動」「ポンプのモーター用」の「ポンプ」は品目にしない。「開閉」「流れを止める」は、品目の名前が出ていないときだけバルブとみなす。
- 登録商品の品目は、分類（例「耐熱ガラス・鋳物」）より先に商品名で判定する。
- 要約と見積フォームの下書きには、型番・条件・数量（最新の値）・お届け先を「伺った条件」として先頭に入れ、最初に伝えた文と直近の文を残す。苦情や相づちは入れない。
- 「何時までに頼めば当日発送？」は当日出荷の締め時刻、「フォームで内容を書き直せる？」はフォームの編集、「送料はいくら？」は送料、「値引きの件は承知しました」は了承として扱う。

### よくある質問への回答（管理画面）

管理画面「設定」の「よくある質問への回答」に、営業時間・見積回答の目安・送料の考え方・来社での引き取りを書くと、チャットはその文をそのまま案内する。空欄の項目は「担当者が確認します」と答える（値を作らない）。

## 生成AIへの指示と検査

- お客様のこれまでの発言（`customerNotes`）と直近8メッセージを渡す。お客様が書いた数値（25A、40度など）は回答で繰り返してよい。
- 選定の確認項目（`selection_points`）、会社の公開情報、取扱分野、担当者への相談方法を根拠として渡す。
- 価格・送料・割引・在庫・納期の数値、約束（「無料です」「確保します」「間に合います」）、販売可否の断定、根拠のない対応範囲（英語対応等）、非公開の取引先、URLは検査で拒否する。「お約束できません」のような否定文は拒否しない。
- 拒否した場合は理由を添えて1回だけ書き直させる（応答開始から7秒以内の場合）。それでも通らなければ、後述の組み立て回答に切り替える。
- 確定回答の後に続ける補足では、確定回答の言い換えの文（文字の組の45%以上が確定回答と同じ）を表示しない。直前2回の返答をほぼそのまま繰り返す文も、ほかに表示する文があれば省く。
- 入力の項目名（facts等）、自社を「御社」と呼ぶこと、お客様が言っていない「お急ぎ」、根拠のない加工・施工の対応（「丸切り加工も承っています」）も拒否して書き直させる。
- 返答の中の電話番号は1回まで。2回目以降の電話番号を含む文は文ごと省く（番号だけ消すと「急ぎの場合はへお電話」のように壊れたため）。
- 本文に書かれたボタン名は、実際に表示するボタン名に直す。ボタンを表示しない返答では、ボタン名を含む文を省く。

## 生成AIが使えないとき

`lib/server/consultation.ts` が会話から回答を組み立てる。お客様の条件（数値・単位・材質・流体など）を復唱し、話題（バルブ、パッキン等）ごとの確認ポイントのうち、まだ伺っていない項目を1つだけ聞く。「分からない」と言われた項目は聞き直さない。条件がそろえば担当者への相談を案内する。商品名・型番の入力を求める定型文は返さない。

## 担当者への引継ぎと見積への誘導（2026-10-13更新）

- 価格・在庫・納期・見積・注文・値引き・送料・支払・見積の回答時期の質問、数量の提示、「扱っていますか」「買いたい」「手配」などの発言は購入の意思とみなし、回答の下に「この内容で見積を依頼する」ボタンを出す（登録商品なら商品の見積フォーム、未登録品なら見積依頼フォーム）。一度出したら、要約や相談の返答でも見積依頼のボタンを出し続ける（ボタン名が途中で変わらないように）。登録商品の価格を答えた直後には、見積依頼の案内を一度だけ添える。
- 見積依頼にも会話IDを付けて保存し、会話を「担当者に引継ぎ済み」にする。管理画面「見積」の明細編集から「チャットの会話とAI調査メモを見る」で、会話と調査メモを開ける（2026-10-13までは見積依頼に会話が紐づいていなかった）。
- 登録されていない型番（例「B60」「6205DDU」）は「登録商品にはありませんが、お取り寄せを含めて担当者が確認します」と答え、取扱いがないような言い方をしない。メーカー名・数量を既に伝えられていれば聞き直さない。
- 前の質問と別の品目（例: 鋳物部品の後の「SUS304の板のほうは？」）を聞かれたら、前の登録商品の価格では答えない。
- それ以外は、相談が2往復以上続いたとき、または要約・手続き・相談方法・取引条件の質問のときに「この内容で担当者に相談する」ボタンを出す。
- ボタンを押すと、会話IDを付けてフォームを開き、「ご相談内容」にお客様の発言（またはAIの要約）を入れておく。
- 電話番号は1つの会話で1回だけ案内する。2回目以降は、電話番号を添えるだけの文を省く。お客様が電話番号・連絡先・営業時間を尋ねたときは、改めて答える。

## 前回の相談

最後のやり取りから12時間たつと、次に開いたときは新しい相談として始まる。前回分はお客様のブラウザ（localStorage）に保存し、チャットの「過去の相談」から閲覧のみで開ける。保存は最大10件・30日で、この端末から削除できる。サイトのDBには追加の保存をしない（現在の会話は従来どおりサーバーに保存され、担当者が確認できる）。

## 担当者向けのAI調査（2026-10-13追加）

管理画面の「AIによる価格・納期の調査（担当者向け）」をオンにすると、価格・在庫・納期・送料を聞かれた未登録の品目について、回答を返した後に調査する。結果は会話の詳細の「AI調査メモ」に表示し、お客様には表示しない。

1. Jevが、調査が必要か（購入の情報を求めているか、品目を特定できるか）と、調べる項目を判定する。キーがない場合はルールで判定する。
2. OpenAIのWeb検索（既定 `gpt-5-mini`、環境変数 `OPENAI_RESEARCH_MODEL` で変更可）で、メーカー・通販サイト・運送会社を調べる。分野が一致する登録済み仕入先のサイトも、サイトを指定して別に調べる。
3. このサーバーが出典ページを開き、記載が本当にあるかを照合する（ページで確認済み／一部のみ確認／ページの記載と不一致／自動取得できず未確認）。金額・日数は単位ごと（「¥18,700」「2〜3日」）、寸法などの数値は数値として探す。「翌日」「在庫あり」のような短い語は、ページにあっても「一部のみ確認」にとどめる。検索で訪れていないサイトのURLは捨てる。
4. Jevが、各記載がその品目（送料なら北九州発・お届け先までの区間）に当てはまるかを判定し、一致度として表示する。ページにお客様の型番・サイズが見当たらない記載や一致度50%未満の記載には「別の型式・サイズの可能性」と表示する。

お届け先は、発送元の「北九州から」を除いて、お客様が最後に挙げた都道府県（なければ主な都市）から判定する。数量は「1本いくら」「1枚あたり」のような単価の言い方を除き、書かれたとおり（例「10個、6個」）に記録する。仕入先サイトは、品目そのものの分野で選ぶ（「ポンプのモーター用のベアリング」でポンプの仕入先を調べない）。要約から「〜してください」などの依頼文を除く。

調査は1つの会話で3回まで、同じ品目・項目・お届け先・数量の重複は省く。登録商品で価格と納期が登録済みのときは、送料だけを調べる。確認用（デモ）の商品は調べない。

## Jevの位置づけ

管理画面で「Jev＋OpenAI」を選ぶと、商品が特定できない質問でJevが取扱分野・資料候補を推定する。推奨構成（OpenAIのみ）では使わない。生成AIが会話全体を読んで分野を判断するため、分類の待ち時間（中央値約0.6秒）と、分類の不採用（信頼度不足）を避けられる。判断の根拠は改善報告を参照。

## 実装の基準

- `lib/chat-policy.ts`: 質問意図、あいさつの切り分け、要約・引継ぎ・手続き・方針の判定、振り分けと理由コード。
- `lib/server/providers.ts`: ローカルの意図判定（材料記号 SUS304 等を型番と誤認しない）。Jev等の分類。
- `lib/server/chat-replies.ts`: 価格・在庫・納期・税込計算、手続き・引継ぎの回答。
- `lib/server/consultation.ts`: 確認ポイント、条件の抽出、方針の回答、AIが使えないときの回答・要約、フォームへの下書き。
- `lib/server/ai-responses.ts`: 生成AIへの指示、出力検査、書き直し。
- `lib/server/chat.ts`: 文脈の引継ぎ、確定回答と生成回答の結合、引継ぎボタンの判定、保存。
- `ChatMessage.route` / `composed` / `handoff` / `handoffDraft` / `factDetail`: 振り分け理由、会話に依存する回答か、引継ぎボタン、フォームの下書き、税込・送料等の追加回答を保存する。再読込時も公開設定の変更を反映する。
- `chat.routed`: 操作履歴の項目。理由コード、分類方式、回答方式（`success` / `success_after_retry` / `failed_or_ungrounded` 等）、外部検索の利用、所要時間を記録する。
